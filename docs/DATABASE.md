# Database Design — Smart Lab Monitor

## 1. Purpose

This document defines the database structure for storing Smart Lab Monitor telemetry, device information, and alerts.

The project will use:

- **SQLite** for the current local prototype.
- **PostgreSQL** as the planned production/cloud database.

The migration to PostgreSQL will be performed separately. The existing SQLite database must remain intact during development.

## 2. Database Architecture

```text
ESP32
  |
  v
Flask Backend / MQTT Worker
  |
  v
Telemetry Validation Service
  |
  v
Database Layer
  |
  +---- SQLite (current prototype)
  |
  +---- PostgreSQL (planned production)
```

Both REST and MQTT messages must pass through the same validation and storage service.

## 3. Proposed PostgreSQL Tables

### 3.1 devices

Stores registered monitoring devices.

| Column | Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary key |
| device_id | VARCHAR(100) | Unique device identifier |
| device_name | VARCHAR(150) | Human-readable name |
| location | VARCHAR(150) | Laboratory or room |
| is_active | BOOLEAN | Device enabled or disabled |
| last_seen | TIMESTAMPTZ | Last received message |
| created_at | TIMESTAMPTZ | Registration time |

### 3.2 telemetry

Stores sensor readings received from ESP32 devices.

| Column | Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary key |
| device_id | VARCHAR(100) | Device identifier |
| message_id | VARCHAR(150) | Unique message identifier per device |
| schema_version | INTEGER | Telemetry schema version |
| timestamp | TIMESTAMPTZ | Device measurement time |
| temperature_c | DOUBLE PRECISION | Temperature in °C |
| humidity_rh | DOUBLE PRECISION | Relative humidity in % |
| voltage_v | DOUBLE PRECISION | Voltage in V |
| current_a | DOUBLE PRECISION | Current in A |
| power_w | DOUBLE PRECISION | Power in W |
| energy_wh | DOUBLE PRECISION | Energy in Wh |
| mq2_raw_adc | INTEGER | Raw MQ-2 ADC reading |
| mq2_voltage_v | DOUBLE PRECISION | MQ-2 sensor voltage |
| presence | BOOLEAN | LD2410 presence detection |
| status | VARCHAR(20) | NORMAL, WARNING, or ALERT |
| raw_payload | JSONB | Original received JSON payload |
| received_at | TIMESTAMPTZ | Backend reception time |

A unique constraint must prevent duplicate messages for the same device:

`UNIQUE (device_id, message_id)`

Sensor values may be NULL when a sensor is unavailable or its reading is invalid.

### 3.3 alerts

Stores alert events generated by the monitoring system.

| Column | Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary key |
| device_id | VARCHAR(100) | Device identifier |
| telemetry_id | BIGINT | Related telemetry record |
| alert_type | VARCHAR(100) | Type of alert |
| severity | VARCHAR(20) | WARNING or ALERT |
| message | TEXT | Alert description |
| created_at | TIMESTAMPTZ | Alert creation time |
| acknowledged | BOOLEAN | Whether alert was acknowledged |

## 4. Indexing Strategy

The PostgreSQL database should include indexes for:

- `devices.device_id`
- `telemetry(device_id, timestamp)`
- `telemetry(received_at)`
- `alerts(device_id, created_at)`
- Unique constraint on `telemetry(device_id, message_id)`

These indexes will improve device-specific history queries and alert retrieval.

## 5. Data Storage Rules

1. Store timestamps using UTC.
2. Preserve the original JSON payload in `raw_payload`.
3. Validate incoming telemetry before database insertion.
4. Reject invalid message structures.
5. Prevent duplicate messages using the device ID and message ID.
6. Store unavailable sensor measurements as NULL.
7. Do not interpret uncalibrated MQ-2 raw ADC readings as gas concentration in ppm.
8. Record backend reception time separately from the device measurement timestamp.

## 6. SQLite Prototype

The existing SQLite database is used by the current Flask prototype.

Current database file:

`database/sensor_data.db`

Keep this database and its existing records during migration.

Do not delete or overwrite it when PostgreSQL is introduced.

## 7. PostgreSQL Migration Plan

The migration will be performed in stages:

1. Review the existing SQLite schema and records.
2. Create the PostgreSQL database and tables.
3. Configure database connection settings using environment variables.
4. Implement a shared database access layer.
5. Connect the Flask backend to PostgreSQL.
6. Test telemetry insertion and retrieval.
7. Verify duplicate-message handling.
8. Verify REST and MQTT use the same storage service.
9. Preserve SQLite until PostgreSQL has been tested successfully.
